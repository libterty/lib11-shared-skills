# Communication RIQC（工作回報與高壓提問應對）

## Authority（權威性）

這是「工作進度回報／被提問／臨時任務指派」這類情境下的**預設且最高優先**內容結構——自動套用，不用等使用者輸入 `/communication-riqc` 或明確要求。**不限於對上回報**：對象可以是主管、GM、董事長、客戶，也可以是平行的同事（跨團隊協調、互相請求支援或決策）、或下屬（交辦任務、更新方向、回應下屬的提問或反彈）——只要是「需要對方理解、決定、或採取行動」的工作溝通，都適用同一套判斷方式，只是 Output Contract 的強調重點依對象不同（見 Workflow 第 3 點）。

適用範圍比 `communication-writing` 窄：`communication-writing` 管**所有**要送給別人看的文字要怎麼寫；這個 skill 管的是**工作回報/被提問類**內容要涵蓋什麼、怎麼排序。兩者同時適用時，先用這個 skill 決定內容的 R/I/Q/C 結構，再用 `communication-writing` 的寫作規則把每一段實際寫清楚（短句、自然語氣、拿掉官腔）。

這條標準的優先權高於一般的專案風格偏好，但不高於：系統指令、安全規則、事實正確性、法律/公司合規要求、以及使用者當次明確提出的例外要求。

**核心心法**：溝通的終點不是把資訊講完，而是促成對方的理解、決策或行動。不只回答對方問了什麼，也要回答對方真正擔心什麼；不只回答對方擔心什麼，也要推動對方接下來要做什麼。沒有下一步的溝通，視為尚未完成。

## Trigger

- 任何一方（主管/GM/董事長/客戶/平行同事/下屬）問「最近怎麼樣」「進度如何」「為什麼還沒完成」
- 向上回報（GM、董事長、總監、主管、客戶）
- **平行協作**：跨團隊/跨部門請求支援或決策、同事之間交接工作、對等單位提出的疑問或抱怨、需要說服平行團隊配合的請求
- **向下管理**：交辦任務給下屬、回覆下屬對優先順序/範圍/資源的提問、下屬對決策提出質疑或反彈、需要糾正方向但不打擊士氣、1-on-1 裡下屬回報進度或困難
- 撰寫週報、日報、專案更新、會議摘要、1-on-1 更新
- 回覆 Slack、Teams、Email，或口頭追問
- 面對客戶、主管、同事或下屬的質疑、挑戰、或帶攻擊性的問題（例如質疑能力/資歷/決策）
- 說明風險、延遲、阻塞、事故、技術債、跨部門依賴
- 需要對方（不論上下平行）提供方向、資源、授權、優先級、或決策
- 使用者提供大量零散背景資訊，要求整理成「可以對上/對外/對下報告」的版本
- 下班前或臨時被指派任務（或臨時要指派任務給別人），需要先釐清再回覆

## Required Input

- 溝通對象是誰（GM/董事長/直屬主管/客戶/平行同事或其他團隊/下屬），以及溝通方向是對上、平行、還是對下
- 目前的事實狀態（進度、完成度、遇到的問題）——有 Source ID 更好，見 `_shared/conventions.md` §2
- 原本的目標/承諾是什麼
- 已知的風險/延遲原因（如果有）
- 是否已經有正在考慮的選項/建議
- 如果以上任一項不足，依 Missing-Data Behavior 處理，不要憑空假設或虛構

## Workflow

1. **判斷 Question Behind the Question**——先問自己：對方為什麼現在問這個？真正擔心什麼？想確認哪一類事項？聽完後需要做什麼？不要只回表面問題，也不要臆測對方的人格或惡意，要把推論轉成可被工作資訊支持的假設（依 §3 標記為 Hypothesis）。常見對照：「最近怎麼樣」通常在確認有沒有風險/要不要介入；「為什麼還沒完成」通常在確認延遲原因/影響程度/責任歸屬/恢復計畫；「你確定這樣可以嗎」通常在確認判斷依據/風險/失敗備案。

2. **用 R-I-Q-C 四段組織內容**：
   - **R（Recap）**：一兩句建立共同背景——目前在處理什麼、目標/承諾是什麼、現在到哪個階段。不重講專案歷史，只留這次判斷必要的背景，讓對方 10 秒內知道「這是在講哪件事」。
   - **I（Insight）**：給出事實之外的判斷——關鍵發現、根因、趨勢、風險、機會、取捨、對交付或商業的影響。區分「事實」和「判斷」，避免「持續處理中」「目前正常」這種沒有資訊量的話，要能回答「所以呢？」。指出問題後要盡快移到「影響 → 判斷 → 方案」，不要把大部分篇幅停留在描述問題有多嚴重（除非對方明確要求根因調查）——建議順序是「問題 → 影響 → 判斷 → 方案 → 下一步」，而不是「背景 → 歷史 → 誰做了什麼 → 更多細節 → 最後才講重點」。例：不要只寫「API 整合有一些延遲，會再持續確認」，要寫「API 整合延遲 10 天，已影響原定上線時程；建議上線延至 8/25，由 Platform Team 本週五前確認可交付日期」。
   - **Q（Question）**：明確的決策請求，附選項與建議（決策/優先級/授權/資源/風險接受/需要主管的經驗或人脈），不要用開放式的「怎麼辦」把問題丟回去。能自己決定的不要升級給主管。如果不需要主管介入，要明講「目前不需介入」，不能整段省略。
   - **C（Call to Action）**：誰負責、接下來做什麼、何時完成或再次回報、交付物是什麼。不能用「持續追蹤」「盡快處理」這種沒有 owner/時間的話收尾；時間未知時至少給下一個確認時間點。任何會議、討論或問題回報，結尾都不能只停留在「資訊交換」——收斂到下一步是誰、做什麼、何時、是否需要對方確認或提供資源，才算完成一次溝通閉環。

3. **依溝通對象調整強調重點**：
   - GM/董事長/高階主管：商業與客戶影響、交付風險、是否需要決策、選項與建議、時間/成本/責任——避免過多技術細節、每日流水帳、無法量化的「快完成了」，也不要把團隊內部執行問題直接丟給高層。
   - EM/技術主管：根因、技術取捨、依賴與阻塞、品質與可靠性、owner 與交付時間。
   - 客戶：客戶受到的影響、已完成的控制措施、恢復計畫、下一次更新時間——避免未經確認的責任歸屬與承諾（呼應 `_shared/conventions.md` §5、§6）。
   - 平行同事/其他團隊：這件事跟對方的關聯與依賴、需要對方配合或決定什麼、時間壓力、對彼此工作的影響——用「我們共同要解決的問題」框架，不用上對下的命令語氣，也不用討好、模糊訴求。
   - 下屬/團隊成員（你在交辦或回應時）：背景與目標、優先順序、完成標準、時間期待、可自主安排的空間；下屬對你提出質疑或反彈時，同樣套用第 4 點的高壓提問應對模式（承認事實→重新定義問題→給證據→回到下一步），不用權威壓下去，也不需要為了維持和氣而模糊掉真正的期待與 deadline。

   **接受度判斷（Stakeholder Acceptance）**：處理敏感、負面、或有挑戰性的內容時，除了分析事實，也要判斷對方是否可能感到被否定、被指責、或失去控制，並選擇更容易促成合作與決策的呈現方式——例如先承認共同的客觀限制（產業環境、系統性因素），再切換到「接下來可以怎麼改善」，而不是停留在「誰做得不好」。這不是淡化風險或隱瞞問題（仍要遵守 §2-§4 的事實與 Source ID 規則），而是提高訊息被接受、被執行的機率。

4. **高壓或攻擊性提問**（質疑能力、資歷、地位）：不要立即防衛或反擊；承認無須否認的客觀事實 → 把問題重新定義成真正需要確認的事 → 用過往經驗/成果當證據 → 回到這次會怎麼交付。維持自信但不羞辱、不挑釁對方。

5. **臨時任務指派**——雙向都適用：
   - 被指派時（尤其下班前）：先釐清工作內容、預估工時、真正期限、完成標準、是否可延到隔天、跟既有任務的優先衝突，確認完再承諾，不要當場空口答應。
   - 指派給別人時（尤其對下屬）：講清楚背景/為什麼是現在、明確的完成標準與期限、是否會影響對方既有優先順序（並主動確認）、對方可以怎麼回饋困難或反對意見——不要只丟一句「這個你來弄一下」就結束，也不要用職權壓過對方合理的疑慮。

6. **依使用場景選擇輸出格式**：30 秒口頭回報（R/I/Q/C 各 1-2 句，共 4-8 句）、Slack/Teams 短訊（【背景】【判斷】【需確認】【下一步】，80-180 字）、Email 正式更新（含主旨）、或高階主管一頁式（Green/Yellow/Red 狀態 + Executive Recap + Key Insight and Business Impact + Decision/Support Needed + Next Actions and Checkpoint）。專案狀態類回報可選附 RAG 燈號：Green（按計畫，無須介入）、Yellow（有風險但可控，需要監控/協調/局部決策）、Red（已影響承諾或即將失控，需要立即決策/資源介入）。

7. 產出前套用 Self-Review Checklist；沒通過就重寫，不要直接輸出未經檢查的版本。

8. 最終文字仍要套用 `communication-writing` skill 的寫作品質規則（短句、自然語氣、拿掉官腔與 AI 腔調、結論放最前面）——這個 skill 決定「講什麼、怎麼排」，`communication-writing` 決定「怎麼寫得清楚」。

## Output Contract

R｜I｜Q｜C 四段式回報，依場景選擇對應格式：

| 格式 | 長度/結構 |
|---|---|
| 30 秒口頭回報 | R/I/Q/C 各 1-2 句，共 4-8 句 |
| Slack/Teams 短訊 | 【背景】【判斷】【需確認】【下一步】，80-180 字 |
| Email 正式更新 | 主旨 + Recap + Insight + Question/Decision Needed + Call to Action |
| 高階主管一頁式 | 狀態（Green/Yellow/Red）+ Executive Recap + Key Insight and Business Impact + Decision/Support Needed + Next Actions and Checkpoint |

- Q 段落如果判斷不需要主管介入，要明講「目前不需介入」，不能整段省略
- C 段落必須包含負責人、行動、時間或下一個 checkpoint
- 涉及專案狀態時，可選附 RAG 燈號，但燈號要有 Fact 支撐（呼應 `delivery-health-review` 的規則：沒有 Fact 不能標綠燈）

## Safety Constraints

- 不得虛構進度、數字、日期、成果、客戶反應——事實性內容仍要遵守 `_shared/conventions.md` §2、§3（Source ID、Fact/Pattern/Hypothesis 標記）。
- 不得把猜測或對他人動機的臆測包裝成確定事實。
- 不得只描述忙碌程度而不說明成果與影響。
- 不得把可以自行決定的事情升級丟給主管當 Q。
- 面對攻擊性提問時，不得使用挑釁、羞辱、或權力對抗語言反擊對方。
- 不得用「我覺得應該」「可能大概」「盡快處理」當作最終承諾——Call to Action 要具體。
- 對客戶溝通時，不得做出未經確認的責任歸屬或承諾（呼應 §5、§6，任何對外訊息仍是待審閱的草案）。

## Missing-Data Behavior

- 資訊不完整時，先用現有資訊產生可用版本，不要因為缺一個小細節就不產出。
- 關鍵未知資訊標示 `[待確認]`。
- 最多主動補問一個「會改變結論」的高價值問題，不要連環追問使用者。
- 資訊不足以形成 Insight 時，不得虛構，要明講：「目前可確認的是＿＿」「根因仍待＿＿驗證」「在確認前，暫以＿＿作為工作假設」（並標記為 Hypothesis）。

## Self-Review Checklist

- [ ] 是否回答了問題背後真正的問題，不只是表面問題？
- [ ] 對方能不能在 10 秒內理解背景（R）？
- [ ] 是否提供了 Insight（判斷/影響），而不只是活動清單？
- [ ] 是否說清楚風險與影響？
- [ ] Q 是否具體、而且真的需要對方回答（或明講不需介入）？
- [ ] 是否提供了建議選項，而不是把問題整個丟給對方？
- [ ] C 是否包含負責人、行動、時間或 checkpoint？
- [ ] 是否避免「持續追蹤」「盡快」「應該沒問題」這類模糊用語？
- [ ] 面對質疑時是否維持專業自信，沒有過度防衛或反擊？
- [ ] 對 GM/董事長而言，內容像不像決策資訊，而不是工作日誌？
- [ ] 是否從「問題」快速移到「影響 → 判斷 → 方案」，而不是停留在描述問題有多嚴重？
- [ ] 結尾是否收斂到明確的下一步（誰、做什麼、何時），沒有下一步就不算完成？
- [ ] 敏感/負面內容是否用對方容易接受的方式呈現，同時沒有淡化事實或隱瞞風險？
- [ ] 最終文字是否已套用 `communication-writing` 的寫作規則？

## Anonymized Eval Case

### Scenario

虛構工程師 Sam 要跟主管回報：「訂單 API 還沒完成，前端這週一直改需求，後端很忙。有開會討論，應該下週可以完成，但不確定。」

### Expected Behavior

- 先判斷主管的 Question Behind the Question：主管真正想知道的是「這件事會不會影響原訂的交付承諾、需不需要我介入」，不只是「進度到哪」。
- 輸出用 R/I/Q/C 重組：
  - R：這是本週原定完成的訂單 API，核心流程已完成，但前端新增了欄位與錯誤處理需求。
  - I：延遲主因不是開發速度，而是需求在實作階段持續變更；若全部納入本週目標，將無法完成整合測試，預計延到下週三（Insight 要標明這是 Hypothesis 還是有事實根據的 Fact）。
  - Q：建議本週先凍結需求、交付原定範圍，新增項目排入下一版；請主管確認是否接受這個拆分方式。
  - C：若今天確認，後端會在週五前完成 API，前端下週一整合，週三提供驗收版本。
- 不會輸出「目前 API 持續開發中，團隊會盡快完成」這種沒有結論、沒有 owner/時間的版本。

### Failure Modes Tested

- [ ] 是否只回覆表面的「進度到哪」，沒有判斷主管真正想確認的風險/是否需介入？（不應該）
- [ ] I 段落是否只是重複列出做過的事，沒有給出判斷或影響？（不應該）
- [ ] Q 段落是否用開放式「怎麼辦」把問題丟回主管，而不是給選項+建議？（不應該）
- [ ] C 段落是否用「持續追蹤」「盡快」這種沒有 owner/時間的話收尾？（不應該）
- [ ] 延遲原因是否被包裝成確定 Fact，而實際上只是團隊的推測？（不應該，要標 Hypothesis）
