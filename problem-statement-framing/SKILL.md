# Problem Statement Framing（問題定義收斂）

## Trigger

- 主管/客戶/自己丟出一個模糊的任務或問題（例如「我們要增加營收」「幫我看一下這個團隊怎麼了」），還沒拆解成可分析的具體問題就想直接開始做
- 準備要跟主管討論一個新任務前，想先確認自己有沒有漏掉關鍵資訊，帶著初步框架去問，而不是空手說「我不知道怎麼做」
- 覺得團隊/利害關係人對同一個「問題」理解不一致，想回頭確認問題定義本身有沒有共識

## Required Input

- 原始的模糊問題/任務描述（照實提供，即使很籠統，附 Source ID，例如 `SRC-USER-INPUT-原始任務`）
- （選填）背景脈絡：最近發生了什麼、為什麼是現在
- （選填）已知的關係人名單與角色
- （選填）已知的限制條件（時間/預算/人力/品質要求）
- （選填）目前手上已經有的資料/研究/專家意見

## Workflow

1. **Basic question**：把使用者提供的原始問題原文列為 Fact。檢查這句話本身是不是已經是一個症狀或解法偽裝成問題（例如「我們該不該裁員」其實是更上層問題的其中一個解法選項），如果懷疑是這種情況要標示為 Hypothesis 並列出建議的反問（「我們真正需要解決的問題是什麼？這句話背後想解決的痛點是什麼？」），不能自己斷言真正的問題是什麼。
2. **Context**：如果使用者有提供背景脈絡，列為 Fact 並附 Source ID；沒有提供就標示 `未提供`，並列出 2-3 個建議追問問題（「為什麼是現在？最近有什麼變化？」）。
3. **Decision makers & stakeholders**：如果使用者有提供關係人名單，依「決策者／champion／可能否決者／會影響決策的關鍵利害關係人／僅供參考意見者」分類列出，各附 Source ID；沒有提供就標示 `未提供`，並明確註明這是整套框架裡最容易被忽略、但風險最高的欄位，附建議問法（「誰一定要同意？誰不能反對？還要先跟誰對齊？」）。
4. **Criteria for success**：檢查使用者提供的成功定義是不是只到「增加」「改善」這種籠統詞彙，如果是，要求進一步定義層級的細節（是哪個數字、怎麼計算、比較哪個期間、有沒有附帶條件如員工滿意度或法規），不能自己假設一個具體數字或計算方式；使用者有提供時附 Source ID。
5. **Solution space / scope**：如果使用者有講明哪些解法/部門/產品/市場可以動，列為 Fact 並附 Source ID；沒有提供就標示 `未提供`，並列出建議問法（「可以改產品嗎？可以跨部門嗎？涵蓋哪些地區？」）。
6. **Constraints**：整理使用者提供的時間/預算/人力/品質限制，各附 Source ID；如果使用者沒有明確排序「快/好/省」的優先順序，必須要求使用者排序，不能自己假設一個排序，並附建議問法（「不可移動的期限是什麼？預算上限多少？哪一個條件最不能犧牲？如果限制不變，是否願意調整成功標準或縮小範圍？」）。
7. **Key sources of insights**：列出使用者已經提到的資料/專家來源，附 Source ID；並針對還沒查過的部分，建議應該先看哪些資料、找哪些人。如果使用者提到多位專家意見不一致，明確提醒需要交叉驗證（了解每位專家的背景與視角、區分長期不變的產業規律和近期變化、擴大訪談樣本），不能只憑一位專家的意見就全盤採信。
8. 彙整七個欄位，產出一份「資訊缺口清單」：哪些欄位標示了 `未提供`，依風險程度排序（Decision makers 與 Constraints 通常風險最高，優先列在前面），每個缺口附建議的詢問對象（例如「跟直屬主管確認」「找財務對齊預算」）與建議確認時間點（例如「下次 1-1」「正式分析前」）。如果缺口很多，明確建議使用者先帶著這份初步框架去跟主管/利害關係人確認，而不是直接跳進分析或空手去問「我不知道怎麼做」。

## Output Contract

- **Basic Question**（原始問題原文，Fact，附 Source ID；如果懷疑是症狀/解法偽裝成問題，標示 Hypothesis 並附反問建議）
- **Context**（已知事實，各附 Source ID；或 `未提供` + 建議追問問題）
- **Decision Makers & Stakeholders**（決策者/champion/可能否決者/關鍵利害關係人/僅供參考意見者分類列出，各附 Source ID；或 `未提供` + 建議追問問題）
- **Criteria for Success**（已知的成功定義，附 Source ID；或需要進一步釐清的具體提問）
- **Solution Space / Scope**（已知的範圍邊界，附 Source ID；或 `未提供` + 建議追問問題）
- **Constraints**（時間/預算/人力/品質限制，附 Source ID 與使用者排序後的快/好/省優先順序；或要求排序的提問）
- **Key Sources of Insights**（已知的資料/專家來源，附 Source ID；建議查詢的資料與建議諮詢的對象；如果有多位專家意見不一致，附交叉驗證提醒）
- **資訊缺口清單**（依風險排序，哪些欄位還需要使用者/主管補充；每個缺口附建議的詢問對象與建議確認時間點，不是只列問題不列該找誰）
- **延伸使用**（選填）：Decision Makers 欄位確認後可以接 `shared-skills/role-clarity-decision-rights/SKILL.md` 產出決策權責提案；問題精確化之後如果是策略類任務可以接 `shared-skills/strategy-execution-mbto-check/SKILL.md`；如果是要準備一場會議來解決這個問題，「今天需要討論的部分」可以接 `shared-skills/meeting-question-decomposer/SKILL.md` 再串 `shared-skills/meeting-agenda-draft/SKILL.md`

## Safety Constraints

- 絕對不能自行幫使用者填答任何欄位的具體內容——不能編造決策者名單、成功指標數字、範圍邊界、或限制條件，沒有提供就必須標示 `未提供` 並附建議追問問題。
- 不能把使用者提供的原始問題直接當成「真正的問題」而不做任何檢查——尤其當輸入本身像是解法或症狀而不是問題時，要標示為需要進一步釐清的 Hypothesis，不能自己斷言真正的問題是什麼。
- Constraints 欄位不能假裝「快、好、省」可以同時最大化，也不能在使用者沒有明確排序時自己假設一個排序。
- Decision Makers & Stakeholders 欄位如果包含真實姓名/職稱（例如誰可能否決、誰是關鍵利害關係人），要標示這是敏感人事資訊——如果這份輸出之後會被轉貼給比原始使用者更大範圍的對象（例如透過「延伸使用」串到其他 skill 或會議材料），使用前要先確認是否需要去識別化或縮限分享範圍，不能預設可以原封不動轉發。
- 建議的專家/資料來源不能只給一個就當作足夠——如果使用者提到的專家意見彼此不一致，必須提醒需要交叉驗證，不能自己選邊站採信其中一方的判斷。

## Missing-Data Behavior

- 七個欄位中任何一個完全沒有輸入資訊，要標示 `未提供`，並列出 2-3 個具體的建議追問問題，不能留白，也不能自己假設答案。
- 如果原始問題本身模糊到連 Basic Question 都無法確認範圍，優先處理這一步，其餘六個欄位標示「問題尚未精確化，以下為基於目前模糊描述的初步版本」。

## Self-Review Checklist

- [ ] 七個欄位都有出現，沒有欄位被跳過不提
- [ ] 每個標示 `未提供` 的欄位都附了具體的建議追問問題，不是空白
- [ ] 沒有替使用者編造決策者名單、成功指標數字、範圍邊界、或限制排序
- [ ] Constraints 欄位有要求使用者排序快/好/省，沒有自己假設排序
- [ ] 如果原始問題本身像是解法或症狀而非問題，有標示為需要進一步釐清的 Hypothesis
- [ ] 資訊缺口清單有列出，依風險排序，且每個缺口都附了建議詢問對象，不是只列問題
- [ ] 多位專家意見不一致時，有提醒交叉驗證，沒有自己選邊站
- [ ] 每個有 Fact 內容的欄位都附了 Source ID，不只是 Basic Question 和 Context
- [ ] Decision Makers & Stakeholders 欄位如果包含真實姓名/職稱，有標示敏感人事資訊、提醒分享前先確認範圍

## Anonymized Eval Case

### Scenario

虛構情境：工程經理「林經理」收到 GM 的任務——「我們今年要提升團隊的工程效能」，只有這一句話（`SRC-USER-INPUT-原始任務`），沒有提供其他背景、關係人、成功標準、範圍、限制、或資料來源；後續補充「主要是因為上季有兩個重大功能延期，董事會有問到工程產能」（`SRC-USER-INPUT-補充脈絡`）。

### Expected Behavior

- Basic Question 要指出「工程效能」定義模糊（可能是 deploy 頻率、PR cycle time、或團隊滿意度），列出建議追問問題，不能自行認定是哪一種；原文附 `SRC-USER-INPUT-原始任務`。
- Context 根據補充內容列為 Fact，附 `SRC-USER-INPUT-補充脈絡`，不能只因為有了這句話就停止追問——仍要確認「兩個重大功能延期」的具體細節是否足夠。
- Decision Makers 標示 `未提供`，明確註明這是常被忽略但風險最高的欄位，附建議問法：「這件事誰要簽核？工程以外還有誰會被這個改變影響？」缺口清單裡要標示建議詢問對象（例如「跟 GM 確認董事會關心的具體是哪個面向」）與建議時間點（例如「下次跟 GM 對齊時」）。
- Criteria for Success 標示 `未提供`，具體指出「提升」需要哪些細節（指標、目標數字、衡量期間），不能自己假設一個數字。
- Solution Scope 標示 `未提供`，附建議問法（可以改流程嗎？涵蓋所有團隊還是特定團隊？）。
- Constraints 標示 `未提供`，要求追問時間/預算/人力限制，並提醒不能同時要求快、好、省，需要林經理自己或跟 GM 確認優先順序。
- Key Sources 建議先查現有 DORA 指標與過去 retro 記錄，並建議找做過類似專案的其他 EM 確認，不自行假設有哪些資料存在。
- 資訊缺口清單要列出五個欄位缺資訊（Context 已有初步 Fact），每項附建議詢問對象與時間點，並建議林經理帶著這份初步框架去跟 GM 確認，而不是直接開始做分析。
- Decision Makers 欄位如果之後被使用者提供了真實姓名（例如某位可能否決的副總），要標示這是敏感人事資訊，提醒分享這份框架前先確認範圍。

### Failure Modes Tested

- [ ] 是否自己幫忙編造了決策者名單或成功指標數字，而不是老實標示 `未提供`？（不應該）
- [ ] 是否把「提升工程效能」直接當成已經夠具體的問題，沒有要求精確化？（不應該）
- [ ] Constraints 欄位是否自己假設了一個快/好/省的排序？（不應該）
- [ ] 資訊缺口清單是否被省略，或假裝分析已經完整？（不應該）
- [ ] 資訊缺口清單的每一項是否都缺少建議詢問對象與時間點，只列問題不列該找誰？（不應該）
- [ ] 如果 Decision Makers 欄位包含真實姓名，是否沒有標示敏感人事資訊、沒有提醒分享前先確認範圍？（不應該）
