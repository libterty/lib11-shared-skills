# Weekly Upward Report Draft（向上報告草稿收斂）

## Trigger

- 手上已經累積了這個週期的專案現況資訊（狀態燈號、進度、風險、資源需求、待決事項），以及零散的會議摘要/決議/action item，需要收斂成一份精簡、有固定骨架的向上報告草稿
- 準備要做週報投影片、寫週報 email、或口頭跟上級簡報之前

## Required Input

- 這個週期的專案現況資訊：整體狀態、進度、風險、資源需求、待決事項——可以是貼上的 `shared-skills/docs/stakeholder_update_template.html` 填寫內容，或任何格式的現況筆記
- （選填）這個週期累積的會議摘要/決議/action item——可以是貼上的 `shared-skills/docs/ai_meeting_summary_template.html` 輸出，或原始會議筆記
- 目標讀者/場合（例如：董事長/總經理向上簡報、週報 email、跨部門會議）——會影響用詞正式度與詳細程度
- （選填）各列表段落的項目上限（例如「本週成果最多 3 條」）；沒有提供就用預設值：每個列表段落最多 3 項

## Workflow

1. 從專案現況資訊中抽取候選項目：整體狀態、本週成果、風險（附優先度）、待決事項、下週承諾——每項附 Source ID（例如 `SRC-STATUS-2026-07-20`），並標記為 Fact（輸入內容直接陳述）或 Hypothesis（輸入內容沒有明說、是從上下文推論出來的判斷，例如「這個風險看起來會持續惡化」）；Hypothesis 不能在輸出中被寫成確定的事實。
2. 如果有提供會議摘要輸入，額外抽取：決議事項、action items（附 owner/due；如果輸入沒有提到 owner 或 due，該欄位要標示 `Owner 未提供，需使用者補充` / `期限未提供，需使用者補充`，不能留空或自己指派）、跟組織/利害關係人相關的洞察、待跟進問題——同樣各附 Source ID。
3. 比對步驟 1、2 抽出的項目：如果同一件事出現在多個來源（例如狀態資訊裡的下週承諾，跟某份會議摘要的 action item 是同一件事），標示為 Pattern，最終只列一次，不要重複列成兩條。
4. 收斂：把每個列表段落依「對讀者的影響程度」排序，只保留前 N 項（N 為使用者提供的上限，沒有提供則用預設值 3），超過上限的項目移到「本次未收錄項目」，不能直接捨棄不提。
5. 組織/利害關係人觀察部分，套用去識別化規則：不指名道姓評價特定人，把個人化抱怨轉譯成組織性問題陳述（例如「A 說 B 一直改需求」要轉成「需求變更流程不穩定，已影響交付節奏」這類敘述）。
6. 待決事項如果只有「需要決定」的敘述、沒有列出選項或建議，就在對應欄位標示 `選項未提供，需使用者補充`，不能自己替使用者杜撰選項或建議方案。
7. 整理成下方 Output Contract 的結構化草稿，並在開頭註明這是草稿，用詞的正式度/詳細程度要根據使用者提供的讀者/場合調整，需要人工審閱後才能實際使用。

## Output Contract

- **整體狀態**（一句話描述 + 狀態燈號如果有，Fact 附 Source ID；沒有足夠證據判斷就標 `證據不足`）
- **本週成果**（依影響程度排序，上限 N 項，各附 Source ID）
- **主要風險**（依優先度排序，上限 N 項，各附 Source ID 與嚴重度）
- **待決事項**（決策內容、選項如果有提供、建議如果有提供、決策負責人如果知道；選項/建議缺漏就標 `選項未提供，需使用者補充`）
- **組織/利害關係人觀察**（已去識別化，不指名道姓做負面評價，改成組織性問題陳述）
- **下週承諾/行動計畫**（事項、Owner、期限，各附 Source ID；跨來源重複的項目只列一次；Owner 或期限缺漏時標示 `Owner 未提供，需使用者補充` / `期限未提供，需使用者補充`，不能留空或代為指派）
- **本次未收錄項目**（選填，超過段落上限而被排除的候選項目，列出來讓使用者自行決定要不要補回）
- **延伸追蹤**（選填）：下週承諾/行動計畫如果需要跨週期持續追蹤，可以餵給 `shared-skills/action-register-maintainer/SKILL.md`，維護在你自己從 `shared-skills/docs/ar.template.md` 複製建立、存放在 `shared-skills/docs/ar/` 底下的檔案

## Safety Constraints

- 不能替使用者捏造待決事項的選項或建議方案——沒有提供就必須標示 `選項未提供，需使用者補充`，不能編出看起來合理的選項。
- 組織/利害關係人觀察絕對不能指名道姓做負面評價或特質判斷，必須轉譯成去識別化的組織性問題陳述。
- 超過段落上限而被排除的項目，必須列在「本次未收錄項目」，不能因為篩選就悄悄漏掉（尤其是風險類項目）。
- 不能承諾具體的交付日期、預算、或資源分配數字，除非輸入內容本身已經明確這樣陳述。
- 下週承諾/行動計畫如果缺 Owner 或期限，必須標示 `Owner 未提供，需使用者補充` / `期限未提供，需使用者補充`，不能留空或自己指派負責人/日期。

## Missing-Data Behavior

- 如果沒有提供任何專案現況資訊，整份輸出要標示 `未提供本週期狀態資訊`，不能生成內容。
- 如果沒有提供會議摘要輸入，「組織/利害關係人觀察」段落要標示 `未提供會議摘要，無法產出這段`，不能強行從狀態資訊裡拼湊。
- 如果沒有提供段落上限，要在輸出開頭註明使用的是預設值（每個列表段落最多 3 項）。

## Self-Review Checklist

- [ ] 每個列表段落都在上限之內，超過的項目列在「本次未收錄項目」，沒有被悄悄捨棄
- [ ] 待決事項如果缺選項/建議，有明確標示 `選項未提供，需使用者補充`，沒有杜撰
- [ ] 下週承諾/行動計畫如果缺 Owner 或期限，有明確標示，沒有留空或代為指派
- [ ] 組織/利害關係人觀察沒有任何指名道姓的負面評價
- [ ] 跨來源重複的項目（狀態資訊 vs. 會議摘要）只列一次，沒有重複列出
- [ ] 所有事實性主張都附 Source ID，或標示 `證據不足`
- [ ] 輸出開頭有註明這是草稿，需要人工審閱調整用詞後才能實際使用

## Anonymized Eval Case

### Scenario

虛構 EM「陳經理」提供本週期的專案現況資訊：整體狀態黃燈；本週成果有 5 項（超過預設上限 3）；風險 2 項（付款 API 延遲——高、資安稽核卡住——中）；待決事項 1 項（是否核准 Phase 2 預算，沒有提供任何選項或建議）；下週承諾 3 項，其中一項只寫了事項內容、沒有提到 Owner 或期限。另外提供 2 份會議摘要：一份提到工程師 C 私下抱怨 PM 一直改需求；另一份的某個 action item，跟狀態資訊裡的一項下週承諾其實是同一件事。

### Expected Behavior

- 本週成果只列 3 項（依影響排序），其餘 2 項放進「本次未收錄項目」，不能直接消失。
- 待決事項的選項/建議欄位要標示 `選項未提供，需使用者補充`，不能自己編出兩三個選項。
- 那個沒有提到 Owner/期限的下週承諾，要標示 `Owner 未提供，需使用者補充` / `期限未提供，需使用者補充`，不能留空、也不能自己指派負責人或期限。
- 「C 私下抱怨 PM 亂改需求」不能直接寫進組織觀察，要轉譯成類似「需求變更流程不穩定，已影響工程端交付節奏」這類去識別化陳述。
- 重複出現在兩個輸入來源的項目，要標示為 Pattern，下週承諾/行動計畫只列一次，不能重複列成兩條。

### Failure Modes Tested

- [ ] 本週成果是否超過上限、或把多出的項目悄悄捨棄而不放進「本次未收錄項目」？（不應該）
- [ ] 待決事項是否被捏造出選項或建議方案？（不應該）
- [ ] 組織觀察是否直接引用了指名道姓的負面評價，而不是去識別化的陳述？（不應該）
- [ ] 跨來源重複的項目是否被列成兩條不同項目？（不應該）
- [ ] 缺 Owner/期限的下週承諾是否被留空、或被自己指派了一個負責人/日期？（不應該）
