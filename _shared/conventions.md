# `shared-skills/` 的共用慣例

`shared-skills/` 底下所有的 skill 都要遵守這些規則；本文件是唯一的權威來源——個別 skill 應該連結回這裡，而不是重複陳述內容。

## 1. 唯一來源

`shared-skills/` 是唯一編輯 skill 定義的地方。不要在別處複製一份。

## 2. Source ID 可追溯性

Skill 輸出中每個事實性主張都必須附一個 `Source ID`——一個讓使用者或後續審閱者可以追溯回原始出處的簡短參考（例如 `SRC-JIRA-1234`、`SRC-SLACK-2026-07-01`、`SRC-INTERVIEW-emp014`、`SRC-DASH-costexplorer`）。如果沒有來源，輸出必須明確說明，而不是省略這個欄位。

## 3. Fact / Pattern / Hypothesis 標記

輸出中每一句斷言性的話都必須標記為以下其中一種：

- **Fact（事實）**——直接觀察/回報到的，附有 Source ID。
- **Pattern（模式）**——跨多個 Fact 歸納出的重複趨勢（必須引用它根基的那些 Fact）。
- **Hypothesis（推測）**——未確認的解釋或預測。必須明確標示，絕不能當成 Fact 呈現。

## 4. 禁止捏造

Skill 絕對不能捏造、或讓輸出暗示（在沒有證據的情況下）：

- 客戶承諾或保證
- 調查完成前的 incident 根本原因
- 沒有連結到觀察行為的個人績效判斷
- 沒有根基於陳述過的假設或真實資料的交付日期/成本效益數字

## 5. 對外與對人內容僅限草案

任何由 skill 產出的客戶對外訊息、法律/商業聲明、或人事相關溝通（回饋、績效內容、組織變動），都是**草案**。輸出必須標示這是需要人工審閱簽核之後才能送出/採取行動的草案。

## 6. 不得未經授權採取行動

Skill 只產出分析、草案、與建議。絕對不能宣稱自己已經執行、授權、或代表組織承諾了：

- 破壞性的基礎設施或資料操作
- 雲端環境變更
- 合約或商業性承諾
- 承認客戶端的法律責任

## 7. Skill 必要區塊

`shared-skills/` 底下每個 `SKILL.md` 都必須依序包含這些區塊：

1. `## Trigger`
2. `## Required Input`
3. `## Workflow`
4. `## Output Contract`
5. `## Safety Constraints`
6. `## Missing-Data Behavior`
7. `## Self-Review Checklist`
8. `## Anonymized Eval Case`

`shared-skills/validate-skills.sh` 會做結構性檢查，確認這些區塊都存在，並檢查是否出現一組被禁止在非否定脈絡下使用的絕對承諾用語。

## 8. 資料不足時的預設行為

當必要輸入沒有被提供、或證據不足時，skill 必須：

- 針對受影響的欄位明確輸出 `證據不足`（或當地語言的對應說法），而不是給一個包裝成事實的最佳猜測
- 避免把狀態/嚴重程度/健康指標預設成「看起來安全」的數值（例如絕對不能把一個未知的專案預設成綠燈）
- 列出缺少哪些輸入、以及該怎麼取得

## 9. Eval Case 中的匿名化

Eval case 必須使用虛構的姓名、公司、與專案。不能使用真實客戶名稱、真實員工姓名、或從正式環境系統複製過來的真實 incident 識別碼。

## 10. 書面溝通寫作原則（最高優先——改編自 David Ogilvy〈How to Write〉）

任何 skill，只要輸出包含**要送給另一個人看的文字**——email、Slack/Teams 訊息回覆、送給利害關係人的會議摘要、狀態報告、溝通草案、談話要點——都要遵守這條規則。這是**最高優先**的寫作規範，優先權跟 §5、§6（草案標示、不得未經授權採取行動）相同、互不取代：§5、§6 管的是「能不能送」，這一條管的是「怎麼寫」。

**核心心法**：好的商業寫作不是寫得長、正式、複雜才顯得專業，而是讓對方用最少時間準確理解你的意思，並知道接下來該採取什麼行動。即使有 AI 輔助寫作，溝通的本質沒有改變——依然是人與人之間的溝通；官腔、冗長、無人味的文字只會讓溝通目的失敗。

七項可執行原則：

1. **用平常說話的方式寫**——不要因為是 email/正式報告就自動切換成生硬語氣。草擬前先問：「如果對方站在我面前，我會怎麼跟他說？」
2. **短句、短段落**——讀者只會花一到兩秒掃過內容。盡量能快速回答三個問題：發生了什麼事？為什麼這件事重要？你希望對方做什麼？
3. **不用複雜術語**——專業不等於複雜。能把複雜的事情講得簡單、清楚、不失準確，才是真正的專業。
4. **能短就短，結論放最前面**——不是要湊到某個字數上限，而是講完該講的就停，不要繞圈子鋪陳到最後才講重點。訓練方法：問自己「假如只能講十句話，最重要的是哪十句？」
5. **引用/數據要核對過**——放進輸出的日期、來源、數字只能是有 Source ID 佐證的 Fact（見 §2、§3），不能是拼湊或臆測的內容。
6. **Call to Action 必須明確**——任何以促成行動為目的的草擬內容，必須明確包含：誰需要行動、要完成什麼、何時完成、應該如何回覆。不能只用「以上請參考」這種沒有下一步的收尾。
7. **不確定該不該用書面溝通時明講出來**——如果事情急迫、敏感、複雜，或需要高度共識，草案要附註「建議先當面/口頭溝通，這份文字只是輔助或事後留存紀錄」。

輸出草擬溝通內容前的品質檢核：

- [ ] 對方能不能在一兩秒內看懂重點？
- [ ] 結論/請求是否放在最前面？
- [ ] 有沒有不必要的複雜詞彙或官腔用語？
- [ ] 是否可以再刪掉一半的字數，而不損失重點？
- [ ] 引用的數字/日期/來源是否都有 Source ID？
- [ ] 讀者看完是否清楚知道下一步該做什麼（誰、做什麼、何時、怎麼回覆）？
- [ ] 這件事是否其實更適合當面/口頭溝通，書面只是輔助？

完整流程、讀者分類（高階主管/直屬主管/同儕/HR/客戶各自的開頭順序）、Call to Action 規則，見 [`communication-writing/SKILL.md`](../communication-writing/SKILL.md)——這是這條規則的權威工作流程，本節只放精簡摘要。這條規則不是要你手動呼叫這個 skill 才生效：只要輸出包含要送給別人看的文字，就要自動套用。跨機器/跨 CLI（Claude Code、Codex）要讓這條規則在每次啟動就自動載入，見 `shared-skills/install-global-policies.sh`。

## 11. 工作回報與高壓提問應對原則（最高優先——RIQC）

任何 skill，只要輸出是**工作進度回報、對上回報、或回應主管/客戶的提問與臨時任務指派**，都要遵守這條規則，跟 §10 同為**最高優先**。§10 管所有寫作的「怎麼寫」；這一條管回報/被提問類內容的「講什麼、怎麼排」，兩者同時適用時先套 §11 排結構，再用 §10 把每段寫清楚。

**核心心法**：不只回答對方問了什麼，也要回答對方真正擔心什麼（Question Behind the Question）。

四段結構：

1. **R（Recap）**——一兩句建立共同背景，不重講歷史。
2. **I（Insight）**——給出事實之外的判斷（根因/風險/取捨/影響），不是只列活動清單。
3. **Q（Question）**——具體的決策請求（附選項與建議），或明講「目前不需介入」；能自己決定的不升級給對方。
4. **C（Call to Action）**——負責人、要做什麼、何時完成或下一個 checkpoint，不能用「持續追蹤」收尾。

完整流程、讀者分類（GM/董事長/EM/客戶/團隊成員各自的強調重點）、高壓提問應對模式、輸出格式範本（口頭/Slack/Email/主管一頁式），見 [`communication-riqc/SKILL.md`](../communication-riqc/SKILL.md)。這條規則同樣自動套用，不用手動呼叫；全域自動載入見 `shared-skills/install-global-policies.sh`。
