# Communication Writing（溝通寫作標準）

## Authority（權威性）

這是所有專業寫作任務的**預設且最高優先**標準——自動套用，不用等使用者輸入 `/communication-writing` 或明確要求。任何其他 skill，只要 Output Contract 包含要送給另一個人看的文字（溝通草案、email、訊息、報告），輸出時都要一併套用這個 skill 的寫作規則（見 `_shared/conventions.md` §10）。

這條標準的優先權高於一般的專案文字風格偏好，但不高於：系統指令、安全規則、事實正確性、法律/公司合規要求、以及使用者當次明確提出的例外要求（例如使用者說「這次故意要正式一點」）。

## Trigger

- 撰寫、回覆、改寫、翻譯、潤飾任何要送給別人看的文字：email、工作訊息（Slack/Teams）、向上報告、客戶溝通、HR/招募溝通、簡報文字、推薦信、狀態更新等
- 使用者問「這段用詞恰不恰當／夠不夠專業／夠不夠清楚」時
- 任何其他 skill 的 Output Contract 包含「溝通草案」時（例如 `customer-escalation-management`、`incident-executive-update`、`project-recovery-plan`、`commitment-risk-review`、`feedback-growth-plan`）

## Required Input

- 讀者是誰（高階主管/直屬主管/同儕/HR/客戶等）
- 這段溝通的目的、希望對方做出什麼決定或行動
- 必要的事實/背景（有 Source ID 更好，見 `_shared/conventions.md` §2）
- 期限（如果有）
- 如果以上任何一項沒有給，依 Missing-Data Behavior 處理，不要憑空假設

## Workflow

1. 動筆前先回答五個問題：讀者是誰？他們必須理解什麼？需要什麼決定或行動？哪些背景是必要的？書面溝通是不是對的媒介？
2. 判斷媒介：如果事情很急迫、情緒敏感、政治敏感、高度模糊、容易引發衝突、或需要即時來回協商，先建議當面/口頭溝通，書面只留一份簡短的決議記錄（誰、做了什麼決定、負責人、期限）。
3. 依讀者類型決定開頭順序（見 Output Contract）。
4. 套用寫作規則：
   - 用平常說話的方式寫，不要因為是書面就自動切換成生硬語氣
   - 短句、短段落，資訊優先於形式
   - 結論或請求放最前面，不要讓讀者等到最後才知道重點
   - 拿掉不必要的正式感、重複內容、明顯的 AI 腔調用語（例如「謹此」「敬請卓參」這類套話）
   - 保留必要的證據、風險、但書、決策依據——精簡不等於刪掉讀者需要的資訊
   - 專業術語只在讀者聽得懂時使用，否則用白話解釋
   - **直接不等於尖銳**：降低語氣的攻擊性，而不是降低訊息的清晰度。事實要精確、措辭要尊重，不要為了「委婉」而隱藏結論，也不要為了「直接」而使用帶羞辱、責備或情緒性的字眼（心法：語氣柔和、事實明確、行動清楚）
   - **不要用「我講話比較直，你不要介意」「恕我直言」這類免責聲明**代替真正的措辭練習——這類開場白通常無法降低攻擊性，反而讓讀者提前進入防衛狀態。直接把內容改寫成具體事實＋影響＋期待＋下一步
   - 如果內容是**對他人行為/產出的回饋**，用「觀察到的具體事實 → 造成的影響 → 未來期待的行為 → 可用的方法/資源 → 何時確認改善」的順序組織（不必套死「先讚美再批評」的三明治公式），並且只評論行為與成果，不評論人格或動機
   - 如果內容是**主管對團隊的高壓/風險/事故更新**，語氣要傳遞掌握感而非焦慮——優先講已知事實、目前影響、處理方案、責任分工、下次更新時間；不用災難化描述、不用無明確行動的催促語句、不把自己的緊張感轉移給讀者
5. 如果需要對方採取行動，明確寫出：誰負責、要做什麼、期限（如果知道）、應該如何回覆、如果沒有回應會怎樣（如果相關）。不要用「請查照」「敬請卓參」「謝謝」這種沒有下一步的空泛收尾。
6. 產出草稿前，先跑過 Self-Review Checklist；沒通過就重寫，不要直接輸出未經自我檢查的版本。
7. 先給出完成的草稿本身，不用先解釋你套用了什麼原則，除非使用者要求分析。如果偵測到重大溝通風險（可能引發誤解或衝突），在草稿後面簡短提醒一句。

## Output Contract

**完成的草稿**，開頭順序依讀者類型調整：

| 讀者類型 | 建議開頭順序 |
|---|---|
| 高階主管 | 結果 → 業務影響 → 風險 → 建議 → 需要的決定（不用附時間軸流水帳，除非對方要求） |
| 直屬主管 | 目前狀態 → 關鍵問題 → 建議 → 需要的支持或決定 |
| 同儕 | 任務/問題 → 負責人 → 依賴關係 → 期限 |
| HR/招募 | 直接答案 → 意願或需求 → 只給必要的背景 |
| 客戶 | 客戶受到的影響 → 目前狀態 → 解法或下一步 → 預期時間 |
| 同事/部屬（回饋類） | 觀察到的具體事實 → 造成的影響 → 未來期待的行為 → 可用的方法/資源 → 何時確認改善 |

- 依 `_shared/conventions.md` §5，任何對外或人事相關的草稿要標示「草案——待你自己確認語氣與事實後再送出」
- （選填）**溝通風險提醒**：如果偵測到可能引發誤解、衝突、或不該用書面處理的情境，附一句簡短提醒

## Safety Constraints

- 這個 skill 只管「怎麼寫」，不取代 `_shared/conventions.md` §5、§6——任何對外或人事溝通仍然只是草案，需要人工審閱簽核後才能送出，不能宣稱已經送出或已經生效。
- 不能為了精簡而刪掉讀者需要的證據、風險、但書、或決策依據。
- 不能杜撰事實、日期、數字、承諾——所有事實性內容仍要遵守 §2、§3（Source ID、Fact/Pattern/Hypothesis 標記）。
- 不能用「我講話比較直」「恕我直言」這類免責聲明取代具體、可執行的措辭。
- 對他人行為的回饋只能評論行為與成果，不能評論人格、動機、或個人價值。
- 高壓/風險/事故情境下的草稿不能使用情緒化、災難化、或責備性語言，也不能把撰寫者自己的焦慮感包裝成客觀事實傳遞給讀者。
- 這條寫作標準的優先權高於一般專案風格偏好，但不高於：系統安全規則、事實正確性、法律與公司合規要求、以及使用者當次明確提出的例外要求。

## Missing-Data Behavior

- 不知道讀者是誰：用最保守、最泛用的專業語氣，並在草稿開頭標註「不確定讀者背景，語氣可能需要調整」，不要自己假設對象。
- 不知道期限：Call to Action 裡標示「[請補上期限]」，不要自己捏造一個日期。
- 無法判斷這是不是該當面溝通的情境：預設先問使用者「這件事急迫/敏感嗎？」，不要自己決定用書面處理。

## Self-Review Checklist

- [ ] 讀者能不能在一兩秒內看懂重點？
- [ ] 結論/請求是否放在最前面？
- [ ] 有沒有不必要的句子可以刪掉？
- [ ] 讀起來像不像真人會講的話，而不是官腔或明顯的 AI 腔調？
- [ ] 事實、姓名、數字、日期、引用是否正確、有 Source ID？
- [ ] 讀者看完是否清楚知道下一步該做什麼（誰、做什麼、何時、怎麼回覆）？
- [ ] 負責人與期限是否明確？
- [ ] 這件事是不是其實更適合當面/口頭溝通？
- [ ] 收件人會不會覺得這則訊息有用、且尊重他的時間？
- [ ] 涉及他人行為的內容，是否只評論行為與影響，沒有評論人格或動機？
- [ ] 有沒有用「我講話比較直」之類的免責聲明，取代真正把話說清楚？
- [ ] 如果是高壓/風險情境，語氣是否傳遞掌握感，而不是把焦慮轉嫁給讀者？

## Anonymized Eval Case

### Scenario

虛構工程主管 Alex 要寫一封信給虛構的 VP Jordan，說明「Falcon 專案」因為一個第三方 API 供應商延遲，時程會晚兩週，需要 VP 同意延後功能上線日期。Alex 原本的草稿開頭是三段感謝與寒暄，第四段才提到延遲，結尾只寫「請查照，謝謝」。

### Expected Behavior

- 重寫後的版本第一句就講結論（時程會晚兩週）與需要的決定（是否同意延後上線日期）。
- 保留關鍵事實（第三方供應商延遲的具體原因、對哪個里程碑有影響），不因為精簡而刪掉。
- Call to Action 明確：VP 需要在哪個時間點前給出同意/不同意的回覆。
- 結尾不是空泛的「請查照」，而是具體的下一步。
- 如果判斷這件事帶有時程風險的敏感性，會建議 Alex 考慮先口頭跟 VP 對一次，再用信件留書面紀錄。

### Failure Modes Tested

- [ ] 是否把結論埋在信件中段甚至結尾？（不應該）
- [ ] 是否為了精簡而刪掉時程延遲的具體原因？（不應該）
- [ ] Call to Action 是否含糊、沒有明確期限？（不應該）
- [ ] 是否用「請查照」之類的空泛收尾？（不應該）
- [ ] 是否完全沒有考慮這件事可能更適合先當面溝通？（應該至少提及）
